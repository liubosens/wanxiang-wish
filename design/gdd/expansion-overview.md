# 万象祈愿 · 四系统拓展总览（Phase 5 · design-strategist 交付）

> 任务系统 / 试炼塔 / 图鉴羁绊 / 限时活动 四系统的总体设计：经济联动、进阶石收支测算、依赖关系与实现顺序。
> 所有数值 [PLACEHOLDER]，需按真实 DAU 与留存校准；禁止 magic number 直接上线。

## 1. 目标与背景

四系统共同解决 progression-spec §5 的已识别风险：**进阶石来源不足 → 升星卡在 3 星 → 战力天花板 → 排行榜通胀停滞**。

分工定位：
- **任务系统（quests-spec）**：日常回流引擎，资源产出的"地板"——保证低投入玩家也有稳定进阶石下限。
- **试炼塔（trial-tower-spec）**：进阶石**主产出点**，与战力挂钩的 PVE 推进感。
- **图鉴羁绊（collection-bonds-spec）**：战力第二增长轴 + 冷门卡（R 卡）价值抢救。
- **限时活动（events-spec）**：运营节奏器，纯配置驱动，不引入新硬通货。

## 2. 资源经济联动图

```
                 ┌─────────────── 产出（→ wallet）───────────────┐
                 │                                              │
 每日签到(现有) ──┼─ wish_stone/chest_key/machine_coin/dust/stone │
 任务系统 ───────┼─ wish_stone + stone（日常地板）+ 碎片小额       │
 试炼塔 ────────┼─ stone（主产出）+ fragments/dust（扫荡）        │
 限时活动 ──────┼─ 加码：签到/任务/双倍碎片周（不新增货币种类）     │
 PK(已拍板封顶)┼─ wish_stone + stone（每日奖励胜场上限）        │
                 └──────────────────────────────────────────────┘
                                    │
                 ┌─────────────── 消耗（← wallet）───────────────┐
 抽卡三池(现有) ←─ wish_stone / chest_key / machine_coin          │
 升星(现有)    ←─ fragments + stone（3 星起）                     │
 王者兑换(现有)←─ point_wz                                       │
                 └──────────────────────────────────────────────┘
                                    │
 战力轴：升星/羁绊 → power → 排行榜 / PK / 试炼塔敌力曲线 → 资源回环
```

要点：
- **不新增货币种类**。所有新产出落到现有 wallet 七字段（`dust/wish_stone/chest_key/machine_coin/point_wz/fragments/stone`）。
- 四系统不直接消耗 stone——stone 的唯一消耗口仍是升星（单一消耗口便于通胀监控）。
- 羁绊不产资源，只改战力公式（见 collection-bonds-spec §3）。

## 3. 进阶石收支测算（证明中位玩家可稳步升星）

### 3.1 需求侧（由现有公式推导，非估算）

升到 3/4/5 星分别额外消耗 `stone = (目标星-2) × rarMult`，即：

| 卡 | 2→3星 | 3→4星 | 4→5星 | 单卡到 5 星合计 |
|----|----|----|----|----|
| R (m=1) | 1 | 2 | 3 | **6** |
| SR (m=2) | 2 | 4 | 6 | **12** |
| UR (m=3) | 3 | 6 | 9 | **18** |

中位玩家月需求假设：主力编队中 2 张卡各推进 1 星（3 星区间）≈ `2 × (2~6)` = **6~12 stone/月**；
账号级总需求（编队 5 张全 5 星，混合 SR/UR）≈ `5 × (12~18)` = **60~90 stone**（长线）。

### 3.2 供给侧（月产出公式）

```
月产出 = 30×S_sign×C_sign            // 签到（现有 1/日）
       + 30×S_dailyBox×C_daily       // 每日任务全勤宝箱
       + 4.3×S_weekly×N_weekly×C_wk  // 每周任务
       + F_new×S_firstClear          // 试炼塔新层首通里程碑
       + 30×S_sweep×C_tower          // 试炼塔每日扫荡
       + 30×W_cap×P_win              // PK（封顶后：奖励胜场上限×胜率）
       + S_event                     // 活动周附加（不常驻）
```
其中 `S_*` 为各来源单次产出 [PLACEHOLDER]，`C_*` 为中位玩家完成率假设 [PLACEHOLDER]。

**示例参数**（全部 [PLACEHOLDER]，仅示范量级）：

| 来源 | 单次值 | 完成率 | 月产出 |
|---|---|---|---|
| 每日签到（现有） | 1 | 100% | 30 |
| 每日任务全勤宝箱 | 1 | 70% | 21 |
| 每周任务（2 条含 stone） | 2×2 条 | 80% | 7 |
| 试炼塔首通里程碑（月均新通 2 个里程碑） | 3 | — | 6 |
| 试炼塔每日扫荡 | 0（扫荡给碎片/尘，不给 stone） | — | 0 |
| PK 奖励胜场（上限 1/日） | 1×胜率 55% | 100% | ~17 |
| **合计（不含活动）** | | | **≈ 81** |

> **PK 奖励上限（已拍板，2026-09）**：每日仅前 N 胜（N=[PLACEHOLDER]，建议 5）发放 stone（wish_stone 同理或保留不限，待定 [PLACEHOLDER]）；超限后可无限 PK 但不发奖。上表 PK 行的月产出公式相应为 `30×N×P_win×S_pk`（N 封顶后取 min(实际胜场, N)），示例值按 N=1 的保守口径，实际以 N 定稿值重算。详见 competitive-spec §7 修订节。

### 3.3 结论

- 中位玩家月需求 6~12，月供给 ≈ 81 [PLACEHOLDER 示例值]，**供需比 ≈ 1:7~1:13，缺口问题消除**。
- 供给侧刻意做成"地板远高于中位需求、低于肝帝总需求"：账号级总需求 60~90 意味着活跃玩家 1~1.5 个月内 stone 不构成卡点，之后长线卡点自然转移到 **UR 收集**（90 抽保底 / 30 币兑换 / 全服保底），与 gdd-03"UR 作长线追逐"的设计意图一致——**stone 从"硬墙"降级为"节奏纹理"**。
- 若 playtest 发现升星过快（power 通胀威胁排行榜），优先调 `S_dailyBox` 与 PK 上限，**不动签到**（签到是回流承诺，砍它伤留存）。

### 3.4 监控指标（上线后校准依据）

- `stone` 钱包存量中位数、P90（周报）。
- 升星动作间隔中位数（升星事件埋点）。
- 试炼塔全服 best_floor 分布（曲线校准用）。

## 4. 系统依赖关系与实现顺序

```
羁绊(bonds) ── 无依赖，纯公式改动（power.ts 三处同源同步）
任务(quests) ── 依赖：draw/upgrade/pk/tower 的事件埋点（bumpQuestProgress）
试炼塔(tower) ── 依赖：power 公式（含羁绊版本）；产出埋点接入任务
活动(events) ── 依赖：任务系统（活动任务组）；卡池配置读取（UP 轮换）
```

**建议顺序**：
1. **羁绊**（最小独立，快赢；先定 power 公式终态，避免试炼塔曲线校准两遍）
2. **任务系统**（埋点基建，其他系统的产出都要被任务计数）
3. **试炼塔**（stone 主产出，依赖前两者的最终形态）
4. **限时活动**（纯配置层，最后拼装；可后置到任何版本）

## 5. 顺带发现的现有系统一致性问题（需用户/主理人知晓）

1. **PK 无次数上限 → 已拍板修复（2026-09）**：原 `handlers/pk.ts` 胜利 +1 stone 且不限次，构成无限刷进阶石漏洞。拍板结论：每日仅前 N 胜（N=[PLACEHOLDER]，建议 5）发放奖励，超限仍可无限 PK 但不发奖；`pk_attempt` 任务计数不受上限影响（见 quests-spec §5）。落地修订见 competitive-spec §7。
2. **稀有度枚举不一致**：`a1_standard_v1` / `c2_roulette_v1` 产出 `SSR` 稀有度（`ssr_nova` 等），而 `RAR_WEIGHT/DUP_FRAG/RAR_MULT` 只认 `R/SR/UR` → 这些卡战力计 0、重复卡转 0 碎片。属存量 bug，不归本四系统范围，但羁绊清单**只基于三世界 R/SR/UR 卡**设计，规避此坑。
3. **migration 缺列**：`db.ts` 读写 `avatar/total_draws/pk_win/pk_lose/last_daily_at`，但 `0001_init.sql` 无这些列（应有未提交的 0002）。新增四系统表建议放 `0003_expansion.sql`。

## 6. 总体风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| stone 供给过调 → power 通胀 → 排行榜失真 | 高 | 3.3 的调参顺序；赛季软重置（competitive-spec §4）兜底 |
| 四系统同时上 → 认知过载（红牌项） | 高 | 分版本灰度（§4 顺序）；每日任务 ≤4 条；UI 不新增常驻入口，任务并入现有签到页 |
| 事件埋点遗漏 → 任务进度对不上 | 中 | 任务进度只信服务端计数（quests-spec §5）；上线前埋点对账清单 |
| 活动配置错误（时间/奖励写错） | 中 | events-spec §6 的配置校验 + 灰度开关 + KV 60s 缓存可秒级回滚 |
